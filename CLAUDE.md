# Budgeteer — Claude Code Context

## What This App Is

**Budgeteer** is a family budgeting PWA. It reads bank statements via Claude (PDF/image → structured transactions), syncs in real time across household members via Phoenix PubSub, and includes a shared grocery list.

See `PLAN.md` for the original, historical build plan. The active engineering
backlog is tracked below in **Engineering Hardening Backlog** and **Future
Work — Prioritized Roadmap**.

---

## Stack

| Layer | Choice |
|---|---|
| Backend + Frontend | Elixir + Phoenix + LiveView (PWA, no separate JS framework) |
| Database | PostgreSQL |
| Background jobs | Oban (`statements` queue, for statement-parsing jobs) |
| AI | Anthropic Claude API via `Req` — statement parsing |
| Auth | `mix phx.gen.auth`, generated under the `Households` context (see below) |
| File storage | Local disk in `priv/statements` for now — see Decisions |

---

## Decisions Made During Scaffolding

These deviate from or sharpen the original `PLAN.md` and should be treated as settled unless revisited explicitly:

- **Auth context is named `Households`, not `Accounts`.** `mix phx.gen.auth` defaults to an `Accounts` context, which would collide with the planned bank-`accounts` context (`Budgeteer.Accounts` for `Account`/bank-account records). Ran as `mix phx.gen.auth Households User users`, so `Budgeteer.Households` owns `User`, `UserToken`, `UserNotifier`, and the `Scope` struct (Phoenix 1.8's per-request scoping pattern) — as well as `Household` itself.
- **All primary keys are UUIDs** (`binary_id`), matching the Perks project's convention. Project was regenerated with `mix phx.new --binary-id` for this — check `config/config.exs` (`generators: [binary_id: true]`) if a generator ever produces integer IDs unexpectedly.
- **Account balance is computed, not stored.** The plan's `accounts.balance_cents` (manually maintained) was replaced with `accounts.starting_balance_cents`; current balance = `starting_balance_cents + sum(transactions.amount_cents)`. Avoids drift between a manually-edited field and the actual ledger. Implement this as a query/function in `Budgeteer.Ledger`, not a stored column.
- **Money is stored as cents but never *typed* as cents.** Every `*_cents` field (`accounts.starting_balance_cents`, `transactions.amount_cents`, `categories.budget_cents`) has a matching virtual string field on its schema (`starting_balance`, `amount`, `budget`) that the LiveView forms actually bind to — the user types `"1500.00"`, never `150000`. `lib/budgeteer/money.ex` (`Budgeteer.Money`) is the one place that boundary gets crossed: `to_cents/1` parses the decimal string (via `Decimal`, not floats — see the `Repo.aggregate` gotcha below for why), `to_decimal_string/1` goes the other way for prefilling edit forms, and `format/1` renders a signed euro string (`"-€42.50"`) for display. Each schema's changeset has a small `put_x_cents/1` private step that converts the virtual field into the real one and adds a changeset error if parsing fails. Follow this exact pattern for any new money field (e.g. a future `PriceOrRateRecord.price_cents`) — never expose a raw `_cents` input in a form.
- **EUR-only logic for now, `currency` field kept on `accounts`.** No multi-currency conversion or display logic should be built yet — treat every amount as EUR — but don't remove the column, since the user wants the door open for it later.
- **Local disk storage for statement uploads**, not S3. Path is `config :budgeteer, :statement_storage_path` (defaults to `priv/statements`). Revisit S3 (`ex_aws`/`ex_aws_s3` — not currently a dependency) only when actually deploying.
- **One household per user.** `users.household_id` is a nullable FK (nullable at the DB level only because a user can theoretically exist before being assigned to a household during onboarding) — application logic should treat it as required once registration/invite flow is built. Do not model multi-household membership.
- **Registration creates a household.** The registration form asks for a household name; `Households.register_user/1` creates the `Household` and `User` (as `:owner`) in one transaction — see `lib/budgeteer/households/user.ex` (`registration_changeset/3`) and `lib/budgeteer/households.ex`. Joining an existing household via an invite link is a separate path — see the household invite flow decision below.
- **`/dashboard` is the post-login landing page**, not `/users/settings` (the `phx.gen.auth` default). `BudgeteerWeb.UserAuth.signed_in_path/1` was changed accordingly. It shows total balance across all accounts, this-month totals per category (only for categorized transactions — `Ledger.monthly_category_totals/2`, inner-joined against `categories`, against `budget_cents` if set), and the household's most recent transactions across every account (`Ledger.list_recent_transactions/2`). Read-only — no forms — but still subscribes to all three PubSub topics (accounts/transactions/categories) and reloads on any change, same convention as every other LiveView.
- **Standard Phoenix asset pipeline was added post-scaffold.** `mix phx.new --no-assets` (per `PLAN.md`'s original suggestion of "Tailwind via CDN") leaves `app.js` as an inert placeholder with *no LiveView JS client at all* — forms silently fall back to plain HTML POSTs with no matching controller route. Since this app is LiveView-first, that's not viable even for local dev, so the standard `esbuild` + `tailwind` + `daisyui`/`heroicons` setup (matching a non-`--no-assets` `mix phx.new`) was wired in instead: `assets/` directory, `config :esbuild`/`config :tailwind` in `config.exs`, `watchers` in `dev.exs`, and `assets.setup`/`assets.build`/`assets.deploy` mix aliases. Run `mix assets.setup && mix assets.build` after a fresh clone (or just `mix setup`).
- **Duplicate statement protection**: `statements` has a `file_hash` column with a unique index on `(account_id, file_hash)`, not in the original plan. Compute a SHA-256 of the uploaded file before insert to prevent double-importing the same statement.
- **Household-scoped generators.** `config :budgeteer, :scopes` (`config/config.exs`) defines a `household` scope (`access_path: [:user, :household_id]`, `schema_key: :household_id`) as the **default** — `mix phx.gen.live`/`phx.gen.context` etc. will automatically thread a `scope` param through every generated context function (`list_x(scope)`, `get_x!(scope, id)`, ...), scope queries by `household_id`, assert ownership on update/delete, and set up per-household PubSub broadcasting (`"household:#{household_id}:resource"`) for free. Use this for a resource that's genuinely a simple single-form CRUD — just run the generator, then **delete the generated migration** (tables already exist from the initial scaffolding migrations) and wire up routes/nav manually. `statements` and `grocery_lists`/`grocery_items` both ended up hand-written instead (see their respective Decisions entries) — their real-world interactions (Oban-driven status, inline real-time check/uncheck) don't fit the generator's navigate-to-a-form-page CRUD assumption. A `user` scope (by `user_id`) also exists but is not default — pass `--scope user` explicitly if a future resource is genuinely per-user rather than per-household. Test fixtures: `household_scope_fixture/0,1` in `test/support/fixtures/households_fixtures.ex` (added alongside the pre-existing `user_scope_fixture/0,1` — both just wrap `Scope.for_user/1`, since our `Scope` struct doesn't distinguish scope "kind").
  - **Gotcha for child tables scoped transitively through a parent FK** (like `transactions` through `account_id → accounts.household_id`): the scope mechanism assumes the table has its *own* `household_id` column and will fail loudly (`undefined_column`) if it doesn't. The original schema deliberately didn't put `household_id` directly on `transactions`/`statements` (avoid redundancy — household is reachable via `account_id`). We chose to **add a denormalized `household_id` column via migration anyway** (see `20260726125502_add_household_id_to_transactions.exs`) rather than hand-write scoping for these tables — keeps every resource on the same generator recipe, and makes household-filtered queries not need a join. `statements` will need the identical treatment when that resource gets built.
  - **Gotcha for a second required FK the scope doesn't know about** (like `transactions.account_id`): the generator casts/requires it as a normal field, but nothing sets it automatically the way `household_id` gets set via the scope — the form doesn't (and shouldn't) expose an `account_id` input, so it must be injected server-side. Pattern used in `lib/budgeteer_web/live/transaction_live/form.ex`: `apply_action(:new, ...)` pre-populates the placeholder struct's `account_id` (fine for the live-validate path, which reads off the existing struct), **and** `save_transaction(socket, :new, params)` explicitly does `Map.put(params, "account_id", account.id)` before calling `create_transaction/2` — because `create_transaction` builds a *fresh* `%Transaction{}` from just the submitted params, not from the assigned placeholder, so anything not in the form (and not scope-injected) silently comes back nil and fails `validate_required`.
  - **`Repo.aggregate(query, :sum, :field)` returns a `Decimal`, not a plain integer/float**, even for a `bigint` column — Postgres's `sum()` returns `numeric`. Adding a `Decimal` to a plain integer raises `ArithmeticError`. Always `Decimal.to_integer/1` (or `Decimal.add/2`) before mixing with plain arithmetic — see `Ledger.current_balance_cents/1`.
  - **Virtual fields break generated tests that compare whole structs with `==`.** Once a schema has a virtual field (e.g. `starting_balance`, `amount`, `budget` — see the money-input decision above), the struct returned by `create_x`/`update_x` (virtual field populated from the just-submitted params) will never `==` the same row freshly fetched from the DB (virtual field is `nil`, since it isn't persisted). Fix at the test level, not the schema level: strip the virtual field before comparing, e.g. `account = %{account_fixture(scope) | starting_balance: nil}`. Search `ledger_test.exs` for this pattern before assuming a struct-equality test failure means real broken behavior.
  - **Generated fixtures reuse a static default name** (`"some name"`), which collides with any real `unique_index` the moment a test both seeds a fixture *and* creates another record with the same generator-default name in the same household (this happened with `categories`, which already had `unique_index(:household_id, :name)` from the very first migration — the generated `phx.gen.live` test's own `setup` fixture collided with its own `@create_attrs`). Give fixtures for uniquely-constrained fields a unique default (e.g. `"some name #{System.unique_integer()}"`) rather than assuming the generator got it right.
- **`raw_ai_output`** is encrypted at rest with `Budgeteer.Encrypted.Map`/Cloak. It contains merchant names, amounts, and dates from bank statements. The original plain-`jsonb` decision was superseded by the deployment-hardening round; key rotation and retention are tracked in the engineering backlog below.
- **The Oban worker never creates `Transaction` records.** `Budgeteer.Statements.ParseWorker` only calls the AI client and writes `raw_ai_output` + `status` (`pending → processing → processed | failed`) on the `Statement`. Real `Transaction` rows only get created when the user reviews and confirms extracted rows on `StatementLive.Review` — a bad AI parse can never silently pollute the ledger. `Ledger.Transaction` gained a `statement_id` field (cast, not form-exposed — same "cast but not exposed" precedent as `account_id`) so review-confirmed transactions can be traced back to their source statement.
- **`Budgeteer.Statements` was hand-written, not `mix phx.gen.live`'d**, unlike every other Phase 1 resource — the household-scope generator recipe (see below) assumes a simple user-editable form, and `statements`' fields (`storage_path`, `file_hash`, `status`, `raw_ai_output`) are all system-set, never user input. It follows the exact same shape as `Ledger` by hand (subscribe/broadcast per household on `"household:#{id}:statements"`, scoped `list_x`/`get_x!`/`delete_x`), plus an **unscoped** `get_statement!/1` (arity 1) for the Oban worker, which runs outside a request/user context. `Statement.status_changeset/2` is a separate, unvalidated changeset for the worker's own `status`/`raw_ai_output`/`error_message` writes — no form ceremony needed since it's never fed user input. `statements` got the identical `household_id`-backfill-migration treatment as `transactions` (see the gotcha above) — see `20260727115645_add_household_id_to_statements.exs`.
- **Elixir has no official Anthropic SDK**, so `Budgeteer.AI.Client` (`lib/budgeteer/ai/client.ex`) is raw HTTP via `Req` to `POST /v1/messages`, model `claude-sonnet-5`. It uses **structured outputs** (`output_config.format`, a `json_schema` requiring `transactions[]` + `currency`) rather than a "return ONLY JSON" prompt convention — a successful response is guaranteed-valid JSON, no `Jason.decode!` gamble. No `anthropic-beta` header is needed (PDF input and structured outputs are both GA now, unlike the beta header in `PLAN.md`'s original sketch). The client sits behind `Budgeteer.AI.ClientBehaviour` so `ParseWorker` depends on `Application.get_env(:budgeteer, :ai_client, Budgeteer.AI.Client)` — tests override this to `Budgeteer.AI.ClientMock` (`config/test.exs`), a `Mox` mock (new test-only dep). `config :budgeteer, :anthropic_api_key` is read from `ANTHROPIC_API_KEY` in `config/runtime.exs` (unconditional, not just the `:prod` block, so it's picked up in dev too once set) — **the user adds this key themselves**; without it, uploads still exercise the full pipeline end-to-end but land on `status: :failed` with an auth-error `error_message`, which is expected and still proves the wiring works.
- **Statement upload is a plain multipart HTML form POST, not a LiveView `allow_upload`.** The first attempt used LiveView's native channel-based upload (`allow_upload`/`live_file_input`/`consume_uploaded_entries`), which — in real testing, on the user's own machine — never completed: the entry stayed stuck at 0% and the Upload button (made conditionally `disabled` until `entry.done?` as a first fix attempt) never enabled. Root cause was never conclusively pinned down (LiveView's per-entry upload uses its own `Phoenix.Channel`, `lvu:<ref>`, joined over the *same* transport as the main LiveView socket — a plausible culprit given `app.js` sets `longPollFallbackMs: 2500`, but this couldn't be confirmed with the tooling available). Rather than keep debugging blind, the whole mechanism was replaced: `StatementLive.Upload` now renders a plain `<.form action={...} method="post" multipart>` (Phoenix.Component's `form/1`, which auto-adds the CSRF token and `enctype="multipart/form-data"`) with an ordinary `<input type="file">`, posting to a new `BudgeteerWeb.StatementController` (`POST /accounts/:account_id/statements`, plain Plug pipeline — not inside the `live_session` block, since it's a normal controller action, not a LiveView route). The controller does the SHA-256 hash + disk write + `Statements.create_statement/2` call that used to live in the LiveView. This sidesteps LiveView's upload-channel machinery entirely — no chunking, no per-entry channel join, nothing to silently fail. `Plug.Parsers`'s multipart `:length` was bumped to 20MB (default 8MB) in `endpoint.ex` to fit the 15MB file cap. **If a future upload feature is tempted to reach for `allow_upload` again, try the plain multipart form first** — it's simpler and already proven to work end-to-end (verified against the real Claude API, not just a stub) where the channel-based approach wasn't.
- **A second real bug surfaced after the multipart switch: `Plug.Parsers` (and specifically `Plug.Parsers.MULTIPART`) defaults `:read_timeout` to 15,000ms** — the max idle time allowed between socket reads while the body streams in. On the user's real machine, uploading an actual file took long enough (slow disk, or a cloud-synced folder like iCloud Drive needing to materialize the file first, etc.) that the connection was reset mid-upload with `Plug.Parsers.ParseError: ... "Read timeout"` before the file finished sending — this looked like "the request went nowhere" from the browser's side. **This is a `Plug.Parsers` plug option, not a Bandit/ThousandIsland server option** — don't go looking for `read_timeout` in `http:`/`thousand_island_options`/`http_1_options` in `config/dev.exs`, it isn't there and doesn't affect this. Fixed in `endpoint.ex`'s `plug Plug.Parsers, ...` call: `read_timeout: 120_000` alongside the existing `length: 20_000_000`. Verified directly with a raw-socket script that streams a multipart body in two halves with an 18-second pause between them — before the fix this reset the connection at ~15s; after, it correctly completed. Any future large/slow request body (not just statement uploads) benefits from this same setting.
- **A third, unrelated 15-second-default bug, on the *outbound* side this time: `Req.post` (used by `Budgeteer.AI.Client`) defaults `receive_timeout` to 15,000ms too.** Once the upload itself worked, the very first real-world test (the user's actual multi-page bank statement PDF) still failed — but this time with `%Req.TransportError{reason: :timeout}` on the `Statement`, meaning the file uploaded fine and the Oban worker ran, but Claude's response for a real multi-page document analysis + structured extraction took longer than 15s and got cut off client-side. Fixed by passing `receive_timeout: 120_000` on the `Req.post` call in `lib/budgeteer/ai/client.ex`. Verified against the user's real statement (a real 5-page PDF) end-to-end: uploaded via curl with a real authenticated session, `status` went `processing` → `processed`, and 38 real transactions were extracted into `raw_ai_output`. **Lesson for this codebase: whenever something "times out" or "goes nowhere" with no clear error, suspect a 15-second default somewhere in the stack (Plug, Req, etc.) before assuming an app-level bug** — that's now been the actual root cause twice in a row.
- **Statement processing has an explicit "processing" banner on `StatementLive.Index`**, not just a small table badge — a flash message alone (which fades) plus a badge easy to miss reads as "nothing happened" to a first-time user, per direct feedback. The index now tracks a `:processing_filenames` list (any `pending`/`processing` statement) alongside the stream and renders a spinner-icon `alert-info` banner naming them and explaining that extraction can take up to a minute and updates live via PubSub — no refresh needed. The status badge itself also gets a small spinning icon for `pending`/`processing`. **Deferred, not built**: a notification (e.g. browser push, or an in-app toast) firing specifically when processing *finishes* — flagged by the user as a "consider later" item, not requested yet.
- **The review screen's category suggestion is no longer a dead end.** A suggested category that doesn't match anything existing now has a "Create it" button next to the hint, not just static text — creating a suggestion the user can never act on defeats the point of suggesting it. Clicking it calls `Ledger.create_category/2` with the suggested name and a **type inferred from the row's own amount sign** (negative → `:expense`, positive → `:income` — no extra prompt needed), then auto-assigns the new category to *every* row sharing that same suggestion (case-insensitive), not just the one clicked — verified against the user's real statement, where six separate "Bank Fees" rows all got assigned from a single click. Category creation still never happens silently on the AI's own initiative; it's always a deliberate, one-click user action.
- **No user-facing "Claude"/"AI" wording anywhere** — it's an explicit product decision, not just a style preference: the model is an implementation detail the user should never see named in the UI. `Budgeteer.AI.*` as a module namespace and "AI" in code comments/moduledocs are fine (internal, not user-facing); flash messages, banners, and hints must not mention it. The processing banner says "extracting transactions" (not "Claude is..."), and the review screen's hint says "Suggested: ..." (not "AI suggests..."). Apply this same rule to any future user-facing copy in this app.
- **AI category suggestions.** `Budgeteer.AI.Client.parse_statement/3` takes the household's existing category names (via `Ledger.list_category_names/1`, an unscoped household-id-based lookup for the worker) and includes them in the prompt; the structured-output schema now requires a `category` string per transaction — the closest existing category name, a newly suggested one, or `""`. `StatementLive.Review` matches that name case-insensitively against `@categories` to pre-select the dropdown; when it doesn't match anything existing, the row is left "Uncategorized" with a hint ("Suggested: \"X\"" — not yet a category) rather than silently auto-creating a category — creating categories is still a manual, reviewed action.
- **Grocery lists.** `Budgeteer.Groceries` is hand-written (like `Statements`), holding both `GroceryList` and `GroceryItem` — matches `Ledger`'s "one context module, several resources" shape rather than fighting the household-scope generator for `GroceryItem`, whose primary interaction (tap a checkbox to check/uncheck inline, real-time, without leaving the page) doesn't fit the generator's navigate-to-a-form-page CRUD assumption at all. `grocery_items` had no `household_id` column (only reachable via `grocery_list_id → grocery_lists.household_id`) — got the same denormalized-column migration treatment as `transactions`/`statements` (`20260727224826_add_household_id_to_grocery_items.exs`), so ownership on item ops can be asserted directly, no join needed. Items broadcast on a topic **scoped to their own list** (`"household:#{household_id}:grocery_lists:#{list_id}:items"`), not a household-wide items topic — otherwise everyone viewing any list would get every other list's check/uncheck noise. `check_item/2`/`uncheck_item/2` are dedicated functions (set/clear `checked` + `checked_by_id` together) rather than a generic `update_item` the caller would have to remember to pass `checked_by_id` into correctly — same "server-controlled, not a raw form field" precedent as `Statement.status`. `GroceryListLive.Show`'s `handle_info` uses `stream_insert`/`stream_delete` for the one changed item, **not** the `stream(..., reset: true)` pattern `CategoryLive.Index` uses on every broadcast — check/uncheck is exactly the high-frequency, single-row case a full reset is a bad fit for (item order shouldn't jump every time someone taps a checkbox). Verified real-time behavior with two genuine `live/2` connections as two different household members (`test/budgeteer_web/live/grocery_list_live/show_test.exs`), same technique as the Presence round.
- **"Who's online" presence indicator (`BudgeteerWeb.Presence`).** `use Phoenix.Presence, otp_app: :budgeteer, pubsub_server: Budgeteer.PubSub` — added to the supervision tree in `application.ex` right after `{Phoenix.PubSub, ...}`. Topic is `"household:#{household_id}:presence"`, matching the existing `:resource`-suffix convention. Tracking is centralized in `BudgeteerWeb.PresenceHooks.on_mount/4` (`lib/budgeteer_web/live/presence_hooks.ex`), wired as a second `on_mount` entry on the router's `:require_authenticated_user` live_session (alongside `{BudgeteerWeb.UserAuth, :require_authenticated}`) — **not** injected into the shared `live_view/0` macro in `budgeteer_web.ex`, per that file's own header comment against defining functions in quoted blocks; `PresenceHooks` is exactly the "define an additional module" alternative it asks for. Tracking key is `user.id` (so multiple tabs/sessions from the same person collapse into one "online" entry, not duplicates). **The important gotcha this surfaced**: the app's real top nav lives in `root.html.heex`, which is a dead HTML shell rendered once per browser tab and never touched again by the LiveView socket — a live-updating indicator has to go in `Layouts.app/1` instead (invoked from inside every LiveView's own `render/1`, so it re-renders on every diff). This meant adding an `online_members={@online_members}` attribute to the `<Layouts.app flash={@flash} current_scope={@current_scope}>` call in all ~14 authenticated LiveViews — mechanical, same plumbing already used for `flash`/`current_scope` at each of those call sites, not a new pattern. `PresenceHooks` uses `Phoenix.LiveView.attach_hook(socket, :presence_updates, :handle_info, ...)` to absorb `presence_diff` broadcasts and refresh `:online_members` — this is why no individual LiveView (`DashboardLive`, `AccountLive.*`, etc.) needs its own `handle_info` clause for it; the hook `:halt`s on a presence_diff match so it never reaches the module, and `:cont`s on everything else so existing `handle_info` clauses (PubSub broadcasts for accounts/transactions/etc.) are unaffected. Verified with a real two-LiveView-process test (`test/budgeteer_web/live/presence_hooks_test.exs` — two `live/2` connections as two different confirmed household members, asserting the indicator appears on join and disappears on disconnect); true simultaneous two-tab *browser* verification isn't practical with this session's browser tooling (single shared cookie jar — a second login just replaces the first tab's session rather than adding a second one), so the LiveView-process test is the actual end-to-end proof here, not a substitute for it.
- **Adding a new child to the `Application` supervision tree (e.g. `BudgeteerWeb.Presence`) requires a full `mix phx.server` restart, not just a recompile.** Phoenix's code reloader recompiles and hot-swaps *module* code on each request, but it does not re-run `Budgeteer.Application.start/2` or restart the supervisor — a long-running dev server started *before* a new child spec was added will keep running the old supervision tree forever, with no visible error until something tries to use the missing process. This bit hard here: the dev server had been running continuously since well before `BudgeteerWeb.Presence` was added to `application.ex`, so once the Presence `on_mount` was wired into the router, every *connected* LiveView mount (the initial disconnected/static render is unaffected, since `connected?(socket)` is false then and `Presence.track` never runs) crashed inside `PresenceHooks.on_mount/4` with `** (ArgumentError) ... the table identifier does not refer to an existing ETS table`. Crucially, this failed *silently from the browser's perspective* — the already-rendered static HTML stays on screen (nothing visibly breaks), but the live socket is dead, so any subsequent click/submit genuinely does nothing. This was misdiagnosed at first as a browser-tool click/coordinate issue (surfaced concretely during the grocery-list "new list" form submission) before the actual dev-server logs revealed the real cause. **Whenever a new item is added to `application.ex`'s `children` list, restart the dev server before trusting any subsequent browser verification** — `mix test` won't catch this either, since each test run boots a fresh `Application.start/2`.
- **Household invite flow.** An existing member sends an invite from `/users/settings` (a third form section, email-only, no new route) — `Households.deliver_household_invite/3` builds a hashed token via `UserToken.build_household_invite_token/2` (same pattern as `build_email_token/2`: random bytes, SHA-256 hash stored, plaintext mailed), with `context: "household_invite"`, `user_id` = the **inviter**, and `sent_to` = the invitee's email (this is what locks the invite to one address, same as the magic-link `sent_to == user.email` check). Expiry is 7 days (`@household_invite_validity_in_days`). The invite link is just `/users/register?token=...` — no new route; `UserLive.Registration.mount/3` resolves the token via `Households.get_household_invite/1` and, if valid, hides the "Household name" field, shows "You're joining {household.name}", and renders the email input `readonly` (pre-filled with the invited address — `readonly`, unlike `disabled`, still submits its value, so no extra changeset-level email-match check is needed). Submitting calls `Households.register_invited_user/2` (a `User.invite_registration_changeset/3` that never casts `household_name`, then `put_change(:household_id, household.id) |> put_change(:role, :member)`) instead of the normal `register_user/1` — no new household gets created, and no migration was needed since `Household`/`User`/`UserToken` already had everything required. An invalid or expired token falls back to normal (create-a-new-household) registration with a flash, rather than dead-ending the page. Verified end-to-end in the browser: sent a real invite, registered through it as a second user, confirmed via magic link, and confirmed the new member's dashboard showed the exact same household data (balance, accounts, transactions) as the inviting owner's.
- **Scaffold branding was still showing** — `Layouts.app/1`'s header had the generated `mix phx.new` boilerplate (Website/GitHub/Get Started links, a `v{Application.spec(:phoenix, :vsn)}` caption) and the page-title suffix was ` · Phoenix Framework`. That's a bad look for anything meant to be pinned to a home screen, so it's gone — the header is now just the logo + "Budgeteer" (the online-members badge stays, since that's real functionality), and the title suffix is ` · Budgeteer`. This was scoped as cleanup only, not a redesign — a real visual/branding pass is explicitly deferred as its own future project, not something to fold into incremental feature work.

Root cause is in `Plug.Static` itself, not this app's code: its `:only` option matches the request's *entire first path segment* literally (`deps/plug/lib/plug/static.ex`, `path_status/2`) — fine for directory-style entries (`images`, `assets`; a nested file's digested name doesn't change the first segment), but broken for standalone top-level files, since a digested `manifest-<hash>.json` never literally equals `manifest.json`. This was never caught locally because `cache_static_manifest` (the config that makes `~p` resolve to digested filenames at all) only applies in `:prod`, and this app had never been deployed/digested for real before this round. `favicon.ico`/`robots.txt` have the identical latent bug (confirmed: their digested variants also 404) but it was never functionally hit — nothing in this app requests their digested URLs (browsers/crawlers always request the plain names, and `sw.js` is registered via a literal `"/sw.js"` string in `app.js`, not `~p`). **Fixed** in `endpoint.ex`'s `plug Plug.Static` call by splitting `only:` (directories: `assets fonts images`) from `only_matching:` (standalone root files: `favicon robots manifest sw`) — `:only_matching` prefix-matches instead of exact-matching, which is exactly what `Plug.Static`'s own moduledoc recommends for "digested files at the root." **Lesson for this codebase**: the local dev server can never catch a `cache_static_manifest`/digest-path bug like this — it needs an actual `MIX_ENV=prod` asset pipeline run (or a real deploy) to surface.

- **MCP server: `anubis_mcp` + personal access tokens** (read-only for financial/grocery data; write tools added later for meal planning only — see below). Discussed two auth options (personal access token vs. a full OAuth 2.1 resource server) — chose the PAT, since this is a single-household app, not a multi-tenant service with untrusted third-party clients; the OAuth infrastructure (dynamic client registration, token refresh) would buy nothing here.
  - **Library**: `hermes_mcp`, the package most likely to surface from memory/training data, was renamed/forked to **`anubis_mcp`** and is no longer the recommended path (`hermes_mcp`'s own docs now redirect to the fork) — confirmed via hexdocs/GitHub directly rather than assumed, same diligence as the Ueberauth research. `anubis_mcp ~> 1.10`.

Prefixed `"bgtpat_"` for recognizability if one ever leaks. Ecto structs are converted to plain maps before `Response.json/2` — Elixir's stdlib `JSON.encode!/1` (which `anubis_mcp` calls internally) doesn't know how to encode a raw Ecto struct's `__meta__`.
  - **Verified with a real MCP client round-trip**, not just tests: `curl` through the actual `initialize` → `notifications/initialized` → `tools/list` → `tools/call` sequence against a running dev server, confirming the JSON-RPC/session-header handshake, all 5 tools listed, and real household data returned — this is protocol-level correctness that unit tests calling Elixir functions directly can't catch.
  - **Real bug: the client-side `embeds_many` "add a row" trick doesn't actually work, despite matching the pattern often shown for this.** The first implementation used a `<button type="button" name="recipe[ingredients_sort][]" value="new" phx-click={JS.dispatch("change", to: "#recipe-form")}>` plus `sort_param:`/`drop_param:` options on `cast_embed` — this is the commonly-cited approach for embeds_many "add/remove row" UIs. It silently did nothing in the real browser (tried three ways: synthetic `.click()`, a real coordinate click, and a `ref`-targeted click — all had zero effect, no console error). **The `LiveViewTest` test for it passed anyway**, because the test used `element(view, "#recipe-form") |> render_change(%{...})` to push the sort param directly to the server, which exercises the *changeset* mechanism but completely bypasses whatever the real button-click-to-form-serialization path is supposed to do — a green test that never actually verified the interaction it claimed to. Only caught by a manual browser walkthrough. **Fixed** by abandoning the sort/drop-param mechanism entirely: `phx-click="add_ingredient"` / `phx-click="remove_ingredient"` call plain `handle_event` clauses that read the current embed list off `socket.assigns.form.source` via `Ecto.Changeset.get_field/3`, splice it with `List.insert_at`/`List.delete_at`, and reassign via `Ecto.Changeset.put_embed/3` — no client-side magic, no special params, just ordinary server-side state manipulation. **Lesson for this codebase**: for any interactive multi-step UI (not just embeds_many), a `LiveViewTest` that constructs its own params via `element/2` + `render_change/2` instead of clicking the actual rendered button proves the *server* handles that payload correctly, not that the *button* produces it — prefer `element(view, "button", "Label") |> render_click()` wherever a real element exists, and treat any low-level params-injection test as a fallback that still needs real-browser confirmation.
- **MCP gets its first write tools: `create_recipe` and `create_planned_meal`.** The read-only boundary from the original MCP decision was deliberate (v1 caution), but requested to be lifted specifically for meal planning — the lowest-stakes data in the app — rather than everywhere at once; accounts/transactions/categories/grocery lists all stay strictly read-only, unchanged.

The migration intentionally downgrades existing tokens to `read`, requiring an owner to explicitly re-grant meal writes. Financial and grocery tools remain read-only regardless of token scope.

Test data and the temporary access token were cleaned up from the dev DB afterward.

Also a good fit generally: single Postgres + single Phoenix node is all this app (one household) needs, and Fly's Elixir-release tooling is more turnkey than a hand-rolled VPS systemd/Caddy setup.

## Data Model (as migrated)

```
households
  id (uuid), name
  inserted_at / updated_at

users                              # Budgeteer.Households.User
  id (uuid), household_id (uuid FK, nullable), email, hashed_password
  name, role (string, default "owner"), confirmed_at, locale
  google_calendar (encrypted refresh-token configuration, nullable)
  -- phx_gen_auth fields (users_tokens table also exists)

accounts                           # Budgeteer.Ledger (planned) — bank accounts
  id (uuid), household_id (uuid FK), owner_id (uuid FK, nullable)
  name, bank_name, currency (default "EUR")
  starting_balance_cents (bigint)  -- current balance is computed, see Decisions

categories
  id (uuid), household_id (uuid FK)
  name, color, budget_cents (nullable), type (income | expense)
  budget_alert_sent_for (date, nullable)  -- month a budget alert was last sent, see Decisions
  unique on (household_id, name)

statements
  id (uuid), household_id (uuid FK), account_id (uuid FK), uploaded_by_id (uuid FK, nullable)
  filename, storage_path, file_hash (unique per account_id)
  status (pending | processing | processed | failed)
  raw_ai_output (encrypted at rest; `Budgeteer.Encrypted.Map`), error_message

transactions
  id (uuid), account_id (uuid FK), statement_id (uuid FK, nullable)
  category_id (uuid FK, nullable), added_by_id (uuid FK, nullable)
  date, amount_cents (bigint, negative = debit), merchant, description, notes

grocery_lists
  id (uuid), household_id (uuid FK), name, archived_at (nullable)

grocery_items
  id (uuid), grocery_list_id (uuid FK), name, quantity, unit
  checked (boolean), added_by_id (uuid FK, nullable), checked_by_id (uuid FK, nullable)

events
  id (uuid), household_id (uuid FK), user_id (uuid FK, nullable)
  title, description, date, start_time, end_time
  source (local | google), external_calendar_id, external_id, external_url
```

`Household` and `User` (with `household_id`/`role`/`name` fields) are built out as Ecto schemas in `Budgeteer.Households`, including registration. `Account`, `Transaction`, and `Category` are built out in `Budgeteer.Ledger` (`lib/budgeteer/ledger.ex`, `lib/budgeteer/ledger/{account,transaction,category}.ex`) with full LiveView CRUD — accounts at `/accounts`, categories at `/categories`, transactions nested at `/accounts/:account_id/transactions` (a transaction always belongs to one specific account, so its LiveViews aren't flat like Account's/Category's) and optionally tagged with a category via `transactions.category_id`. `Ledger.current_balance_cents/1` computes each account's live balance from `starting_balance_cents` + the sum of its transactions. Note: `transactions.household_id` was added via migration after the fact — see the scoping gotcha above. `/transactions` (flat, not nested) is a household-wide search across every account — see the transaction-search decision below for why it's separate from the per-account list.

`Statement` is built out in `Budgeteer.Statements` (`lib/budgeteer/statements.ex`, `lib/budgeteer/statements/{statement,parse_worker}.ex`) with LiveViews nested the same way as transactions: `/accounts/:account_id/statements` (index), `/accounts/:account_id/statements/new` (upload), `/accounts/:account_id/statements/:id/review` (confirm/edit extracted transactions). `Budgeteer.AI` (`lib/budgeteer/ai/{client,client_behaviour}.ex`) is the Claude API integration — see the Decisions section above for the full design (worker never auto-creates transactions, structured outputs, Mox-mocked in tests).

`GroceryList`/`GroceryItem` are built out in `Budgeteer.Groceries` (`lib/budgeteer/groceries.ex`, `lib/budgeteer/groceries/{grocery_list,grocery_item}.ex`), with `GroceryListLive.{Index,Form,Show}` — `/groceries` (index, active/archived toggle), `/groceries/new`/`/groceries/:id/edit` (rename), `/groceries/:id` (the real-time shopping-list page: add/check/uncheck/delete items inline). See the Decisions section above for the per-list PubSub topic design and the denormalized `household_id` migration.

- **Navbar unified into a single row.** Prompted directly by a reported bug: the theme toggle rendered *above* the logo, because the app actually had two stacked navbar-like elements — `root.html.heex`'s top `<ul>` (theme toggle + primary nav links, wraps every page including the plain landing-page controller view) and a second, separate `<header class="navbar">` inside `Layouts.app` (logo + wordmark + online-members badges, LiveView-only) — plus `home.html.heex` hand-rolled a *third* copy of the same logo+wordmark markup for the one plain-controller page. Consolidated to one row: the logo/wordmark (via the `<.logo>` component, not a duplicated inline SVG) now lives as the first `<li>` in `root.html.heex`'s own `<ul>`, with `class="mr-auto"` pushing everything else right, followed by the primary links, the theme toggle, then the email/settings dropdown last — reordered from "utility control first" to the conventional brand-left/utility-right layout. `Layouts.app`'s header shrank to *just* the conditional online-members badges (a plain `div`, not a `<header>`) since presence data is a LiveView-socket assign (`@online_members`) that the static root layout genuinely can't access — that part couldn't be merged into the single root nav, only the redundant logo/wordmark could. `home.html.heex`'s duplicate header block was deleted outright once the root layout started rendering the brand unconditionally. Verified in the browser: single-row nav in both themes, correct reordering, mobile still wraps cleanly via the existing `flex-wrap` (no regression of the earlier "flexbox trap" fix), and a raw `curl` of `/` confirmed the logged-out (no-cookie) nav renders Register/Log in correctly with the same single-row structure.
- **AI statement parsing reliability, prompted by a real production flake.** The very first real prod upload (a genuine 5-page Millennium statement, confirmed by inspecting the PDF directly — cleanly formatted, 30+ obviously-extractable transactions) came back `processed` with exactly one transaction, every field blank/zero (`date: ""`, `merchant: ""`, `amount_cents: 0`). Not a code bug — encryption, storage, and the API call all worked correctly; Claude itself returned schema-valid but degenerate JSON. Re-uploading the same file worked fine, confirming a one-off model flake rather than a systemic break. Three changes address this:
  - **`temperature: 0`** added to the `Req.post` body in `Budgeteer.AI.Client` — extraction is not a creative task, and the default (1.0) leaves unnecessary room for exactly this kind of run-to-run inconsistency.
  - **System prompt now explicitly says** to return an empty `transactions` array when nothing is found, rather than a placeholder row — the prompt previously never covered this case at all.
  - **`Client.validate_parsed/1`** (new, private) rejects any response containing a transaction where every field is blank/zero (`date`, `merchant`, `description` all `""` and `amount_cents` is `0`) as `{:error, {:degenerate_response, parsed}}` — deliberately distinct from a genuinely empty `transactions` list, which is a legitimate "nothing to extract" result and is left alone. Verified directly (no `Req.Test` HTTP-stub seam exists for this module yet, so this was checked by re-running the exact private-function logic against real/empty/degenerate/mixed cases) rather than building new test infrastructure for one function.
  - **`ParseWorker` was silently defeating its own `max_attempts: 3`** — every failure branch returned `:ok` (Oban's success value) after calling `mark_failed`, so a statement went straight to `:failed` on the very first hiccup and Oban's retry-with-backoff never actually ran. Fixed: the worker now returns `{:error, reason}` on failure (letting Oban retry normally) and only calls `mark_failed` when `job.attempt >= job.max_attempts` — the statement stays `:processing` through intermediate retries, matching the existing "still working on it" UI banner, and only becomes `:failed` once retries are truly exhausted. Existing tests updated (`statements_test.exs`) to reflect this — one now asserts the mid-retry case explicitly stays `:processing`, another simulates the final attempt (`attempt: 3, max_attempts: 3` passed to `perform_job/3`) to assert the eventual `:failed`. **Trade-off**: a genuinely permanent failure (e.g. a bad API key) now takes a few minutes (Oban's default backoff across 3 attempts) to surface as `:failed` instead of being instant — acceptable given the reliability gained against transient blips, but the "processing" banner's "can take up to a minute" copy is now slightly optimistic for the failure path specifically; not fixed here since it's copy-only, not correctness.
- **UI polish pass, prompted by user-reported bugs plus one worse bug found while investigating them.** Reproduced locally by seeding a realistic processed statement directly in the dev DB (including one deliberately long AI-suggested category name) rather than guessing from code.
  - **Review page**: the category `<select>` and its "Suggested: ..." hint were both broken by the same root cause — `<td>` defaults to `vertical-align: middle`, so when the hint text wrapped across several lines (worse with a long suggested category name), the whole row got taller and every *other* cell's single-line input ended up floating mid-row instead of aligned to the top, which is what read as "buttons not aligned with their row." Fixed with `align-top` on every cell in the hand-rolled review table. Separately, the select itself was truncating its own text (`"Uncategorized"` → `"Uncateg…"`) because nothing gave it a minimum width — fixed with `min-w-40` on the select and `min-w-56`/`max-w-56` on its cell/hint paragraph so both render fully and wrap predictably instead of ballooning.
  - **Nav restructure surfaced a worse bug than "too many items."** The top nav (`root.html.heex`) had 9 items (email + 7 links + log out) on one `justify-end overflow-x-auto` line. Confirmed via the DOM (`scrollWidth === clientWidth`, scrolling had zero effect) that this is a real flexbox trap: content pushed left of the origin by `justify-content: end` isn't reachable by scrolling in most browsers — **Dashboard, Accounts, Categories, Groceries, the theme toggle, and the user's email were completely unreachable from the mobile nav**, not merely crowded. Fixed by grouping `Recipes`/`Meal Plan` under a "More" dropdown and `Settings`/`Log out` under an email dropdown (daisyUI's `<details>`-based menu submenu pattern — no JS needed), cutting visible top-level items from 9 to 6. First attempt kept `overflow-x-auto` for the (now much rarer) overflow case, but that silently clipped the new dropdowns' own popovers — `overflow-x: auto` with the other axis left as its default `visible` forces the browser to treat `overflow-y` as non-visible too (a real CSS Overflow spec rule, not a bug in this app), so anything popping below the nav got clipped by the same container. Replaced `flex-nowrap` + `overflow-x-auto` with `flex-wrap` instead — on a narrow phone the nav now wraps to a second/third line (still fully visible, just taller) rather than either clipping or trapping content unreachably.
- **`CLOAK_KEY` blast-radius reduction, prompted directly by the user asking "isn't there a better way" than an all-or-nothing key.** Two separate, complementary fixes rather than reaching for a KMS/envelope-encryption setup — overkill for a single-household app's actual threat model, and it wouldn't address the more fundamental issue below anyway:
  - **`raw_ai_output` is now cleared once reviewed.** Found while investigating: the field was never cleared after `StatementLive.Review`'s "save" confirms transactions — it sat encrypted, indefinitely, for *every* statement ever uploaded, despite its own documented purpose (see the AI-parsing decision above) being purely temporary staging before real `Transaction` rows exist. `Statements.clear_reviewed/2` (new, scoped) nils it out right after a fully-successful save (`review.ex`'s `handle_event("save", ...)`, `errors == []` branch — deliberately *not* on a partial-failure resubmit, since the LiveView's in-memory `@rows` — not a re-read of `raw_ai_output` — is what drives a retry, but a stale/cleared value would break a future re-`mount` of the same review page before the user ever successfully saves). This is the higher-leverage fix of the two: it shrinks what *any* future key compromise could expose at all, independent of how strong the key itself is — a leaked key now only exposes statements genuinely mid-review, not the household's entire multi-year statement history.
  - **Key rotation is now actually possible without destroying data.** Previously, `Budgeteer.Vault` had exactly one configured cipher — rotating `CLOAK_KEY` (the documented response to a suspected leak) would have made every existing encrypted row permanently unreadable, which is a bad incident-response position to be in (rotate and lose data, or don't rotate and stay compromised). Cloak's cipher list already supports exactly this via multiple named ciphers matched by an embedded tag, so `Vault.ciphers/0` now conditionally adds a `:retired` cipher when `CLOAK_PREVIOUS_KEY` (optional, `config/runtime.exs`) is set: new writes use the new `CLOAK_KEY` as `:default`, but rows still encrypted under the outgoing key keep decrypting via `:retired` until a background pass has re-saved (and so re-encrypted) everything, after which `CLOAK_PREVIOUS_KEY` can be dropped. **Verified for real** — not just reasoned about — using two genuinely separate `mix run` processes (simulating an actual redeploy, not an in-process config hot-swap, which turned out to give a false negative the first time this was tried): encrypted a value under key A alone, then in a fresh process configured key B as default + key A as `CLOAK_PREVIOUS_KEY`, and confirmed the key-A ciphertext still decrypted while new writes used key B.
- **Sudo-mode reauth wall on `/users/settings` hid the very login method a Google-only user has.** `UserLive.Settings` requires `sudo_mode?` (authenticated within the last 10 minutes) via its own `on_mount {UserAuth, :require_sudo_mode}`, redirecting to `/users/log-in` otherwise. But `UserLive.Login`'s "Continue with Google" button was wrapped in `:if={!@current_scope}` — meaning it only rendered for a genuinely unauthenticated visitor, not this reauth case, where `@current_scope` is still set (the on_mount hook loads it from the existing session even though the sudo-mode check failed). A user who signed up via Google and never set a password would hit this wall with no way back in except a magic-link email — the one button they actually use was invisible. Fixed by always showing the button. While fixing this, also threaded `return_to` through the Google round trip the same way the invite flow already threads its token (`UserOAuthController` gained a `stash_return_to` plug alongside `stash_invite_token`, stores it as the session's `:user_return_to` key on callback — the same key the password/magic-link paths already populate via `log_in_user/3`) — without this, re-authenticating via Google would silently drop the user on `/dashboard` instead of back on the Settings page they were trying to reach.
- **Error tracking: Sentry (`sentry` + `finch`).** Chosen over AppSignal for its free tier and native Elixir/Phoenix/LiveView support. `dsn` is read from `SENTRY_DSN` (`config/runtime.exs`) with the same "unset = graceful no-op" tolerance as `ANTHROPIC_API_KEY`/`GOOGLE_CLIENT_ID` — confirmed directly (`mix sentry.send_test_event` with no DSN prints "Event not sent because the :dsn option is not set", doesn't crash).
  - **This app uses Bandit, not Cowboy — that changes the standard setup.** `Sentry.PlugCapture` exists only to rescue exceptions Cowboy would otherwise swallow before Phoenix's own error handling sees them; Bandit doesn't have that problem, so it's deliberately omitted from `endpoint.ex` (only `Sentry.PlugContext` is added, for request-context enrichment). The less obvious consequence: `Sentry.LoggerHandler`'s default `capture_excluded_domains` is `[:cowboy, :bandit]`, on the assumption that `PlugCapture` already handles those crashes — without `PlugCapture`, leaving that default in place would have meant **every Bandit-originated crash silently never reached Sentry at all**. `application.ex`'s `:logger.add_handler/3` call overrides it to `capture_excluded_domains: []`.
  - `on_mount Sentry.LiveViewHook` added to the shared `live_view/0` macro in `budgeteer_web.ex` (applies to every LiveView automatically) — safe to put there directly, unlike `PresenceHooks` (which needed router-level `current_scope`/session access per that file's own header comment against defining functions in quoted blocks); this hook needs neither.
  - Still needs the user's own one-time setup: sign up at sentry.io, create a project, `fly secrets set SENTRY_DSN=...`, then `mix sentry.send_test_event` (with `SENTRY_DSN` exported locally too, if testing dev) to confirm a real event arrives.
- **Data visualization pass — sparkline hover, category-spend breakdown chart.** Prompted directly by feedback that the dashboard's charts "feel a bit lacking." Used the dataviz skill's methodology (form → color → validate → marks → interaction) rather than freehand design.
  - **Balance sparkline gained a hover crosshair + tooltip.** It was a static SVG line — showed the shape of the 30-day trend but no actual date/balance value at any point, which the dataviz skill treats as an incomplete line chart by default (a hover layer is "part of the deliverable, not an upgrade"). Implemented as a `Phoenix.LiveView.ColocatedHook` (this project's existing hook pattern — `phoenix-colocated/budgeteer`, wired into `app.js` already) rather than a separate `hooks.js` file: a vertical crosshair line tracks pointer-X, snapped to the nearest of the 30 data points (index = round(pointer-ratio × (n-1)), no per-point hit-testing needed since points are evenly spaced), tooltip shows date + `Budgeteer.Money.format/1`'d value, and flips from right- to left-anchored past the 70%-width mark so it never overflows the chart's right edge.
  - **New: a category-spend breakdown chart** (`DashboardLive.category_breakdown_chart/1`) — a single horizontal stacked bar, one segment per expense category proportional to its share of this month's total spend, with a legend (swatch + name + amount) below and a per-segment hover/focus tooltip. Complements the existing per-row budget meters (those answer "vs. its own budget"; this answers "vs. everything else"). Only expense categories with actual spend this month are included — income categories and a spend-free month render nothing, rather than an empty/zero chart.
    - **First real use of a categorical (multi-hue) palette in this app** — everything before this was single-hue brass. Used the dataviz skill's validated default 8-hue palette (`palette.md`) verbatim rather than hand-picking colors, added as `--series-1`..`--series-8` + `--series-other` CSS custom properties in `app.css`, keyed off this app's own existing `[data-theme=dark]` mechanism (not the skill's generic media-query snippet, since this app already resolves a concrete `data-theme` at load time via its theme-toggle JS). **Actually ran the validator** against this app's real surface colors (`#f2ede1` light / `#1c1914` dark, not the skill's generic `#fcfcfb`/`#1a1a19` defaults) — both pass; light mode gets a WARN on contrast for 4 of the 8 slots (orange/aqua/yellow/magenta all sit under 3:1 on the cream surface), mitigated by the chart's legend always rendering visible direct-label text for every segment (the WARN's required "relief channel"), not just color.
    - **Color slot is assigned by stable alphabetical order among the household's own expense categories, not by this month's spend rank** — the skill's "color follows the entity, never its rank" rule. Assigning by rank would repaint a category a different color from month to month as spending patterns shift (e.g. Groceries could be blue in a big-grocery month and orange in a big-travel month). Categories beyond the 8-slot cap fold into a single gray `--series-other` segment (summed together) rather than generating a 9th hue, per the skill's series-count ladder — verified directly by seeding 10 real expense categories with transactions: the alphabetically-last 2 correctly merged into one "Other" segment with their summed total, the first 8 each kept their own stable slot.
    - Verified interactively in the browser, not just by reading the code: real seeded multi-category data (cleaned up after) to see actual segment widths/colors/legend, hover tooltip content and position/flip logic, and the categorical CSS variables resolving to the exact validated hex values in both themes.
- **Transaction search — both a global cross-account page and per-account filters, sharing one form component.** Prompted by there being no way to find a transaction other than scrolling a single account's full history or the dashboard's "10 most recent across all accounts." `Ledger.search_transactions/2` (`lib/budgeteer/ledger.ex`) takes a household-scoped query plus an optional filter map (`account_id`, `category_id` — including the literal `"uncategorized"` — `query` against merchant/description/notes via `ilike`, `date_from`/`date_to`, `amount_min`/`amount_max`) and is the one place filtering logic lives. **Amount range matches on the transaction's absolute value**, not signed — a search for "around €45" should find both a €45 expense and a €45 refund, since the user is recalling a magnitude, not a sign. `BudgeteerWeb.TransactionLive.FilterForm` (new, `lib/budgeteer_web/live/transaction_live/filter_form.ex`) is a plain params-in/params-out function component (deliberately not changeset-backed — these fields filter a query, they don't validate or persist anything), reused by both `TransactionLive.Search` (new, `/transactions`, household-wide, includes an Account column and an account-select filter) and the existing per-account `TransactionLive.Index` (gained the same filters minus the account select, since it's already scoped to one account). `Ledger.list_account_transactions/2` was deleted as dead code once `search_transactions/2` (called with `account_id` fixed) superseded its only caller. The `user_return_to`-present case (explicit return-to path, e.g. `/foo/bar`) and the logout redirect (always `/`, untouched by this fix) were already correct and left alone.
  - **Lesson for this codebase**: a test asserting on the *literal* redirect target of a successful login is exactly the kind of test that silently encodes a bug as a spec once the bug ships — worth a second look any time a redirect-destination test is this uniform across otherwise-different login paths (four nearly-identical `~p"/"` assertions across two files should have been a signal, not routine).
- **Also fixed: a GitHub secret-scanning alert on the fixed test webhook secret.** The `whsec_<base64>` value `config/test.exs` and two webhook tests share (see the inbound-email decision above) was flagged as a possible Stripe webhook signing secret — a false positive (it's a synthetic fixture, never used against a real endpoint), but GitHub's scanner pattern-matches on the literal `whsec_`-prefixed base64 string in source, regardless of what it's actually for. Fixed by building it via `"whsec_" <> Base.encode64("test-secret-key-for-signing")` in all three locations instead of a literal — same technique already used one line away in `resend_webhook_signature_test.exs` for a *different* test secret — which keeps the decoded value (and therefore every computed HMAC) identical but leaves no contiguous string in source for the scanner to match. Alert resolved as false-positive via the GitHub API once the fix landed; git history still contains the old value in prior commits, but since it was never a real credential there's nothing to rotate and no reason to rewrite history.
- **Daily morning summary — the first P1 roadmap item, and the first scheduled (not on-demand) AI feature in this app.** `Budgeteer.DailySummary` (`lib/budgeteer/daily_summary.ex` + `daily_summary/{summary,worker,notifier}.ex`) follows `Budgeteer.Insights`' shape closely (same upsert-one-row-per-household pattern, same "all arithmetic in Elixir, the model only phrases it" rule) but is generated by `Budgeteer.DailySummary.Worker`, an `Oban.Plugins.Cron` job (`config/config.exs`, `"0 6 * * *"`), not a LiveView button — there is no manual "generate" entry point at all, since the whole point is a proactive push, not an on-demand pull like budget insights.
  - **No timezone library in this app** (confirmed: no `tzdata` in `mix.lock`, nothing Portugal-specific exists yet beyond the EUR-only convention) — `"0 6 * * *"` is a fixed UTC time approximating a Lisbon morning (07:00 WEST in summer, 06:00 WET in winter), not a true per-timezone schedule. Fine for a single-household, Portugal-only app; would need revisiting for real multi-timezone support.
  - **The worker is a fan-out job, not a per-household trigger** — `Households.list_household_ids/0` (new, unscoped — enumerates every household, since a cron job has no request/user context at all, the most extreme version of the "background job, no scope" precedent already used by `list_household_emails/1` etc.) — and each household's generation is wrapped in its own `case`/`rescue` inside `Worker.run_for_household/1`, so one household's AI failure or crash can never block or retry another's already-delivered summary. `max_attempts: 1` for the same reason: Oban retrying the *whole* job would risk re-emailing every household that already succeeded before a later one failed — if a run genuinely fails, tomorrow's cron fire is the retry, not an immediate one.
  - **Four new unscoped, household-id-based helper functions**, one per context the summary pulls from, each following the exact `list_household_emails/1` precedent: `Meals.get_planned_meal_for_household/2` (today's planned meal, if any), `Events.list_events_for_household/2` (today's events), `Groceries.list_unchecked_items_for_household/1` (unchecked items across active, non-archived lists), and `Ledger.monthly_category_totals_for_household/2` (which `monthly_category_totals/2` now delegates to, rather than duplicating the query). **Deliberately not a fabricated `%Scope{user: %{household_id: ...}}`** — that would've reused every existing scoped function with zero new code, but the signed-in-path bug fixed earlier this same session was *exactly* this kind of thing going wrong: code trusting a `Scope`-shaped value that wasn't really backed by a real `%User{}`. Given that fresh lesson, matching this codebase's own established "add a real unscoped helper" convention was the safer call, not the more convenient one.
  - **Only categories that have actually reached their budget are included** (same `abs(spent) >= budget` threshold `Ledger.BudgetAlertWorker` already alerts on), not every category's spend — keeps the prompt, and the resulting summary, focused on what's actually worth a household member's attention that morning rather than a full budget recap.
  - **Generated AI text is now locale-aware.** DeepSeek receives an explicit language instruction for English or European Portuguese. Insights and daily summaries persist one variant per household locale, and the daily-summary worker sends each member the variant matching their saved locale. This intentionally makes one additional model call when a household uses both supported locales, rather than showing one member another member's language.
  - **Delivered over email and push, both**, reusing `Ledger.BudgetAlertWorker`'s exact dual-channel dispatch shape (`Households.list_household_emails/1` + `Households.list_household_device_tokens/1`, `Push.send/2` already a graceful no-op with no APNs keys configured). The roadmap entry's own wording ("email or in-app") undersold what shipped — the dashboard also gets a small read-only "Today" card (`DashboardLive`, above the balance section) showing the same stored summary, live-updated via the same `subscribe_summary`/`broadcast_summary`/`handle_info` pattern as every other real-time resource in this app; no reason to pick one channel when the underlying data is already computed once and cheap to fan out three ways.
  - **No per-household opt-out or scheduling preference** — the roadmap entry itself flagged this as an open question, deliberately left unscoped for v1, same as every other "not scoped" item that shipped anyway in this app's history (e.g. budget insights' manual-refresh-only choice). Every household currently gets a summary every morning; a future settings toggle is the natural extension if this turns out to be unwanted noise for some households.
  - **Verified against the real household's dev data**: the full pipeline (all four data-gathering queries, then the real DeepSeek call) was exercised directly via `DailySummary.generate_summary_for_household/1` with no `DEEPSEEK_API_KEY` set — reached the real API and failed only at the auth layer (`401`), same "proves the wiring, not a real generation" caveat as every other AI feature verified in this codebase without a key. The dashboard card's rendering (correct in `pt_PT`: "Hoje" header, summary text) was confirmed by inserting/broadcasting a real row directly against the dev DB and reloading — **the live PubSub push specifically was not cross-process-verified** (broadcasting from a separate `mix run` process doesn't reach the running dev server's PubSub, a tooling limitation, not a code issue), but the subscribe/broadcast/`handle_info` wiring is byte-for-byte the same pattern already proven live for `Insights`/`Subscriptions`/every other dashboard card in this app, not a new mechanism. Full `mix test` (442 tests, including new coverage for every new unscoped helper function, the context module, and the worker's per-household isolation) and `mix compile --warnings-as-errors` both pass. Not yet verified against a real `DEEPSEEK_API_KEY` in production, unlike budget insights — worth a real smoke test there given this session's own "any AI-pipeline change can only be considered verified against the real API" lesson from the `temperature: 0` production bug.
- **Read-only Google Calendar import.** `Budgeteer.GoogleCalendar` uses a separate OAuth authorization flow with the existing Google client credentials and the narrower `calendar.readonly` scope; it stores the refresh-token configuration encrypted on the user, syncs the primary calendar through `GoogleCalendar.SyncWorker`, and imports events into the shared calendar with `source: :google`. Imported events remain read-only in Budgeteer and link back to Google. Disconnecting removes only that user's imported events. Two-way writes, calendar selection, and real Google-provider verification remain deferred until this read-only flow has been used successfully.

## Future Work — Prioritized Roadmap

The long-term ambition is for Budgeteer to become a one-stop shop for home management, not just budgeting. None of this is scheduled/committed to a date — this is a priority ordering, not a sprint plan — but capturing it here so nothing gets lost, and so the next session picks up the highest-leverage item first instead of whatever's most interesting.

Priorities below were assigned during a 2026-07-30 competitive-analysis pass against Rocket Money/Monarch/Copilot — see each item for the specific reasoning, since "priority" here means value-vs-effort for *this* single-household app, not a generic feature-parity checklist.

### Shipped

~~Real outbound email provider~~, ~~meal planning~~, ~~OAuth sign-in (Google)~~, ~~MCP integration~~ (read-only for financial/grocery data, write tools for recipes/meal-plan), ~~charts on the dashboard~~, ~~CSV transaction export~~, ~~iOS install-nudge banner~~, ~~recurring-transaction/subscription detection~~, ~~family calendar~~, ~~read-only Google Calendar import~~ (primary calendar, encrypted refresh token, Oban sync; two-way writes and calendar selection remain deferred), ~~in-app AI recipe/ingredient extraction~~ (text-paste and URL — see the Decisions section for the still-deferred photo/PDF scope), ~~European Portuguese localization~~, ~~native iOS app~~ (Capacitor wrapper — see `mobile/README.md` for the remaining Apple-account-gated steps: real device testing, push notification credentials, TestFlight/App Store distribution), ~~budget insights~~ (AI-driven via DeepSeek, manual-refresh v1 — see the Decisions section), ~~inbound statement-email parsing~~ (via Resend Inbound — see the Decisions section for the real Resend Inbound domain/webhook setup still needed before a real statement can flow through it), ~~daily morning summary~~ (AI-driven via DeepSeek, Oban cron — see the Decisions section) — all **done**, see the Decisions section above for each.

### P1 — Next up, worth doing

1. **Meal suggestions from historical data (NTH)** — defer until the household has enough meaningful meal history and the data model records whether a planned meal was actually cooked. A future implementation should rank suggestions deterministically from completion frequency, recency, weekday patterns, variety, and grocery overlap; an LLM is not required for the core feature.

### P2 — Deprioritized (real value, but lower than the above relative to effort)

1. **Investment/net-worth tracking, bill-due-date reminders** — Monarch/Copilot both have these; lower priority since they're not central to this app's actual differentiation (real-time household sync, AI statement import, the combined budgeting+groceries+meals surface) — they're closer to feature parity than to something this app is uniquely positioned to do well.
2. **Live grocery prices from Continente/Pingo Doce** — deprioritized. Neither retailer has a public API, so this is a scraping problem (fragile, breaks on every site redesign, legally grey), not an engineering one. Cheaper alternative worth considering instead: let users optionally log the price when they check off a grocery item, and aggregate it over time — crowdsourced, no scraping.
3. **Recipe extraction from a photo or PDF** — the one remaining input mode now that text-paste and URL extraction have both shipped. Moved down from P1 2026-08-02 per direct feedback ("don't think there's much value there"). Has a proven-safe upload pattern to reuse (`StatementController`'s plain multipart POST) but needs a session-stash-and-redirect detour to hand the result back into `RecipeLive.Extract`'s review phase — not attempted yet, no clean precedent in this codebase for that hand-off.

### Deliberate tradeoffs (not on this roadmap — revisit only if the trigger below actually happens)

- **Full open-banking/PSD2 bank feed integration** (an aggregator like Plaid/Tink/Nordigen) — would remove the AI-parsing step entirely for supported banks, but is a much bigger lift than anything else here: compliance/licensing considerations, a different integration per bank/aggregator, ongoing cost, and PSD2 consent that typically needs renewing every ~90 days. Considered directly against inbound-email parsing (see the Decisions section — that's what shipped instead) specifically because it reuses almost nothing of the existing pipeline; it's a genuinely separate integration surface, not an extension of one. Purely aspirational; no research done on aggregator coverage for Portuguese banks (Millennium, Caixa, BPI).
- **Monetization** — not on an effort/value axis at all; it's trigger-based. Hold off on any billing infrastructure until a household beyond the user's own actually wants to pay, since building it now is pure overhead against zero current demand. When the trigger happens: a per-household subscription gated on the one feature with real variable cost (AI statement parsing — a handful of free imports/month, unlimited on a paid tier), while grocery lists/meal planning stay free. Stripe integration and plan-gating logic are the main pieces of work, deliberately deferred until then.
- **Automating online grocery shopping (Portugal)** — parked 2026-08-02 after real research, not guessed at. Checked every major PT chain for a public/developer API: **none exists**. Continente (Sonae, largest, Salesforce-Commerce-Cloud-powered site, also runs a separate ~30-min dark-store app "Quico") — no API. Pingo Doce (Jerónimo Martins) — only brought online ordering in-house in May 2025 (previously ran through Mercadão/Glovo); delivery is currently Lisbon/Porto only; no API. Auchan — mature online ordering (delivery/drive/600+ pickup points), no API found. Mercadona — **no online ordering in Portugal at all yet** (Spain-only), though heavy PT logistics investment (a €290M hub near Almeirim, 39 stores as of Jan 2026) suggests this could change — worth a fresh check if revisited. Lidl PT — conflicting/unclear signals on whether real online ordering even exists. Glovo/Uber Eats/Bolt Food carry some of these as marketplace listings (Glovo Express does grocery dark-stores), but their public APIs are partner/merchant-side only — nothing lets a third party place a consumer order programmatically. Even **Pepesto**, a real cross-country "European Grocery API" (26 chains, 11 countries) with exactly this ambition, doesn't cover Portugal, and is read-only (catalog/pricing) even where it does — confirming nobody has built ordering-as-a-service for this market yet. **Conclusion**: any automation today would have to be browser automation against a retailer's own site (same "fragile, breaks on redesign" concern already noted for the live-grocery-prices idea above), not an API integration — there's nothing to integrate with. **The trigger to revisit**: either a real conversation with a retailer's own team (Continente is the natural first call — largest chain, most mature site) about whether they'd support this kind of integration, or the idea recurring enough on its own that it's worth building browser automation anyway despite the fragility. If it does get picked back up, the design constraint already agreed on stands: client-side only (a bookmarklet/driven browser session using the household's own retailer login), cart-building only, human reviews and pays — never a server-side integration holding retailer credentials, and never a fully autonomous purchase.
